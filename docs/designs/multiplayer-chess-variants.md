Generated by Office Hours on 2026-11-25

Status: APPROVED

## Problem Statement

Chess Royale currently launches multiplayer through one headset-following world-space canvas. The creator chooses White, Black, or Random, then creates a four-letter room. As soon as a second player fills the other seat, `ChessFusionLobbyState` sets `MatchReady` and immediately publishes the initial board. There is no synchronized match configuration and no pause for the guest to review what the host selected.

The next release should let the host configure a multiplayer match without creating a second menu system. The first playable scope is:

- Standard or Chess960 starting layout;
- Three-check on or off, composable with either starting layout;
- Podium & Overview on or off for both players, while each player controls their own Overview toggle;
- the existing White, Black, or Random host color choice; and
- a new Chess960 position index for every rematch.

Chaos is a later mode. Its no-turn movement, cooldowns, piece weight, and ground-level arena must eventually reuse the same room, board identity, avatar, and rematch infrastructure, but it is not selectable until its simultaneous movement rules are complete.

## What Makes This Cool

One room can produce four complete turn-based experiences without four copies of chess:

1. Standard
2. Standard Three-check
3. Chess960
4. Chess960 Three-check

The host creates the experience in VR, the guest sees the exact same settings before accepting, and Fusion holds one official configuration. Chess960 removes memorized openings, Three-check changes tactical priorities, and the arena option changes the physical experience without changing the chess rules.

## Current UI and Integration Constraints

The implementation should extend `ChessFusionLobbyUI`, not replace it.

- The lobby is already a `RenderMode.WorldSpace` canvas.
- It is `920 × 1040` canvas units, scaled to `0.0014`, positioned about `2.1 m` in front of the active camera.
- It already follows the headset and uses `TrackedDeviceGraphicRaycaster` for controller-ray input.
- It swaps page roots named Choose, Join, Create, Playing, and Rematch on the same canvas.
- The Create page is already the single room-code/waiting window requested in Sprint 4.
- The current Join page includes the in-world A–Z keyboard.
- The current game starts immediately when the second seat fills.

Do not add a webpage, screen-space configuration scene, second popup, scrolling form, or separate configuration prefab. Use the existing palace theme, large segmented buttons, and the same floating panel.

## Decisions

- The host selects the rules; the guest sees a read-only summary and chooses whether to join the match.
- Starting layout, Three-check, and Podium & Overview are independent match settings.
- Podium & Overview means both players receive podiums and access to Overview, but each player enters Overview independently.
- Chaos forces ground-level play and disables Overview when it is implemented.
- A Chess960 rematch keeps all other settings but generates a new synchronized position index.
- The first release uses the existing-controller approach for speed rather than extracting policy interfaces now.
- The architecture ceiling is 7/10. Extract rule policies when Chaos begins, a second simultaneous variant is added, or variant branches affect three or more controller workflows.

## Premises

1. A Fusion network object stores the official configuration. Clients never derive match settings from unsynchronized UI state.
2. The room creator finishes configuration before creating the room. The replicated configuration is immutable during that room; changing it requires returning to Configure and creating a new room.
3. Creating the room is the host's acceptance. The guest explicitly accepts the replicated configuration revision. Match phase, seat connectivity, and pre-match acceptance are separate state so reconnect does not return an active game to configuration.
4. Standard, Chess960, and Three-check continue using authoritative square-to-square move requests, plus an explicit authoritative castle-side action for Chess960's atomic special move.
5. Chess960 implements legal setup and Chess960 castling, not only a shuffled back rank.
6. Three-check counts legal checking moves, counts a double check once, and retains checkmate as a win.

## Approaches Considered

### Selected: Configuration plus switches

Add one replicated match configuration and small, localized branches inside the existing controller, lobby, arena, and network state. This is the smallest change that ships the first three modes.

### Rejected for now: Policy-based rule modules

Cleaner for Chaos, but it front-loads a controller refactor before players receive a new feature. The design records explicit triggers for upgrading later.

### Rejected: ScriptableObject rule assets

Useful for a large designer-authored variant catalog, but premature and more vulnerable to Quest/Editor asset-version mismatches.

## Recommended Integration

### 1. Keep one VR panel and add two page states

Update the existing `LobbyScreen` flow:

```text
Choose
  ├─ Create → Configure → Create/Wait → Playing → Rematch
  └─ Join   → Join Keyboard → Confirm → Playing → Rematch
```

#### Choose page

Keep only three large actions: Create, Join, and Leave. Move the existing color choice into Configure so Join players do not see host-only controls.

#### Configure page (new)

Use the current 920 × 1040 panel without scrolling:

- Header: `CREATE MATCH`
- Starting layout segmented buttons: `STANDARD` / `CHESS960`
- Three-check segmented buttons: `OFF` / `ON`
- Podium & Overview segmented buttons: `OFF` / `ON`
- Host color segmented buttons: `WHITE` / `RANDOM` / `BLACK`
- Compact two-line summary
- Large `CREATE ROOM` button and smaller `BACK` button

Use `ChessUITheme.SetChoice` for selection state. Avoid tiny checkboxes or web-style switches. Every controller target should remain at least as large as the current choice buttons.

Fit the page using the current coordinate system and no scrolling: header near `y=430`, layout row `y=300`, Three-check row `y=180`, Podium & Overview row `y=60`, color row `y=-80`, two-line summary near `y=-210`, Create near `y=-350`, and Back near `y=-445`. Use the existing roughly `260–280 × 72` choice targets. Validate these coordinates in headset before polishing typography.

#### Create/Wait page (extend existing)

Keep the single room-code window. Add a compact read-only match summary under the code plus a `LOBBY` action. The host already accepted these settings by creating the room. To edit them, the host leaves the room and returns to Configure; there are no live configuration edits or seat-reassignment races after a guest joins.

#### Confirm page (new)

After joining a room, do not hide the canvas immediately. Show:

- room code;
- starting layout;
- Three-check status;
- Podium & Overview status;
- the guest's assigned color when available;
- `READY` and `LEAVE` buttons.

The guest cannot edit settings. Ready sends the exact configuration revision shown on the panel; authority rejects a delayed or stale Ready request.

#### Playing and Rematch

Playing continues to hide the lobby canvas. Rematch retains its current result screen and two-player agreement. For Chess960, the authority generates and publishes a new position index before resetting the pieces.

### 2. Add one compact network configuration

Create `ChessMatchConfig` as an `INetworkStruct`, with stable primitive fields rather than Unity object references:

```text
SchemaVersion
GameplayMode        TurnBased | reserved Chaos
StartingLayout      Standard | Chess960
ThreeCheckEnabled
PodiumOverviewEnabled
Revision
```

The Chess960 position is mutable per-round state, not a user-selected match setting. Store it separately as `RoundChess960Index` on `ChessNetworkGameState`. Also replicate a monotonically increasing `RoundSequence`; every initial/rematch snapshot and move request identifies its round so delayed traffic from the previous game is rejected.

Keep the existing creator seat preference alongside the configuration. Time control remains the current default in this release; making clocks configurable is separate scope.

Store the lobby configuration and lifecycle state on `ChessFusionLobbyState`:

```text
MatchConfig
MatchPhase          Configuring | Playing | Ended
WhiteAcceptedRevision
BlackAcceptedRevision
```

State authority validates and writes the configuration once when the creator opens the room. `Revision` identifies those immutable settings. The creator's assigned seat receives that revision as accepted; the guest calls `SetReady(acceptedRevision)`. Authority accepts it only when the sender occupies that seat, the room is still Configuring, and `acceptedRevision == MatchConfig.Revision`.

Do not overload the current `MatchReady` flag with three meanings. Use:

```text
MatchPhase     persistent lifecycle, remaining Playing during a reconnect window
SeatsFilled    current connectivity derived from active WhitePlayer/BlackPlayer
CanStart       Configuring + both seats + both accepted the same revision
CanMove        Playing + sender owns a connected seat
```

This replaces the current behavior where filling both seats immediately starts the match. `PublishInitialBoard()` runs only on the transition from Configuring to Playing. A disconnect during Playing never returns to Configuring and never asks a reconnecting player to accept settings again.

If the creator leaves while the room is still Configuring, close that pre-match room and return the guest to Choose with a clear message. Do not transfer configuration ownership before play. After the match starts, the existing Fusion state-authority handoff and reconnect behavior continue.

### 3. Feed configuration through the current room flow

Extend the current call chain rather than creating another manager:

```text
ChessFusionLobbyUI pending choices
  → ChessFusionRoomManager.CreateRoom(..., config)
  → ChessFusionLobbyState.ConfigureCreator(..., config)
  → replicated MatchConfig
  → guest reviews and accepts exact Revision
  → authority selects RoundChess960Index for this round
  → ChessGameController.ResetGame(config, roundChess960Index)
  → ChessNetworkGameState publishes one complete initial snapshot
  → MatchPhase changes Configuring → Playing
```

The creator's pending UI choices are not authoritative. They become official only after state authority validates and writes them to `ChessFusionLobbyState`. Starting is one authority transaction: increment `RoundSequence`, choose the round index, reset the controller with both the immutable configuration and that index, publish the complete sequence-tagged initial snapshot, then expose Playing. Clients enable moves only after applying the snapshot for the current sequence. They must never observe Playing with an uninitialized or previous board.

### 4. Implement deterministic Chess960 setup

Treat `RoundChess960Index` as a position index in `0..959` with a documented one-to-one mapping. Generate the back rank from that authoritative index with these constraints:

- bishops occupy opposite-colored files;
- the king starts between the two rooks;
- the remaining files contain the queen and two knights;
- Black mirrors White on the same files;
- pawns remain on their normal ranks.

Both clients should receive the round index, but only state authority resets the official board and publishes the resulting `NetworkPieceState` array. Proxies render the published board instead of independently trusting their own generator. On rematch choose `(previous + randomOffset) % 960`, where `randomOffset` is in `1..959`, which guarantees a different position without changing `MatchConfig.Revision`.

`ChessGameController.ResetGame(config, roundChess960Index)` must place pieces on generated starting squares rather than always calling the serialized standard start square. Standard ignores the index. Assign duplicate pieces deterministically by stable piece ID.

Add an explicit arbitrary-square reset method on `ChessPieceInteractable` rather than mutating serialized Standard start data. Standard calls the existing path; Chess960 supplies a generated square for the current round.

### 5. Replace hard-coded castling files for Chess960

The current controller assumes:

- kings begin on file `e`;
- rooks begin on `a` and `h`;
- castling always moves both pieces.

Chess960 requires per-match king and rook origin files. Castling still ends with:

- g-side: king on `g`, rook on `f`;
- c-side: king on `c`, rook on `d`.

Represent castling as an explicit atomic action with side (`CSide` or `GSide`), not as an ordinary king move followed by an inferred rook move. In VR, moving the king to its castling destination initiates castling; when the king already occupies that destination, moving the involved rook to its final square initiates the same atomic action. The request tells authority the castle side, and authority validates and moves both pieces as one state change.

Update castling generation, execution, rights tracking, and repetition keys. Handle legal cases where only the king moves, only the rook moves, or the king and rook exchange squares. Multiplayer Chess960 must not ship until these cases have automated tests.

Chess960 AI and `ChessEngine` support are explicitly out of scope for this multiplayer release. Single-player remains Standard. This avoids expanding the first release into a second rewrite of the engine's hard-coded castling masks.

### 6. Add Three-check counters at the authoritative rules boundary

Track checks delivered by White and Black as bytes in the network game state and rules snapshot. After a successful legal move:

1. evaluate whether the opponent's king is attacked;
2. increment the mover's check count once, even for double check;
3. if the count reaches three, publish a Three-check win;
4. otherwise continue existing checkmate, stalemate, and draw evaluation.

Add `WhiteWinsByThreeCheck` and `BlackWinsByThreeCheck` outcomes so the result panel, audio, and reconnect/rematch flow can describe the actual win condition. Show both counters near the existing clock/status panel only when Three-check is enabled.

If one move both delivers the third check and checkmate, record the result as a Three-check win. Both conditions award the same player, and this precedence makes the selected variant visible. Include both check counters in the repetition-position key; an identical board with different Three-check progress is not the same game state.

### 7. Make arena behavior consume the same configuration

`ChessFusionRoomManager.MoveRigToSeat()` currently always calls `RaiseOntoPodium()`. Gate that call using `PodiumOverviewEnabled`.

- On: create both podiums and allow each player's existing Overview toggle.
- Off: place both players at the ground spawn, hide/disable the Overview control, enable the board-perimeter teleport path, and use direct/near grab for pieces.
- Switching rooms must remove or deactivate generated podiums so a previous room cannot leak its arena into the next match.
- Never synchronize a player's live Overview camera state; involuntary VR camera movement would be uncomfortable.

Give these transitions explicit APIs rather than scene searches spread across callers: `ChessFusionRoomManager.ClearGeneratedPodiums()` and `ChessViewToggle.SetAvailable(bool)`. Turning availability off must first return a local player from Overview to Immersive.

Ground mode is not complete merely because podium generation is skipped. The existing code documents that human-sized back-rank pieces block floor-level controller rays. Add teleportable pads around all four board edges so players can move beside the piece they need, keep controller rays for menus, and make piece movement a near/direct-grab interaction. Ground mode must pass a headset test that every starting piece is reachable without shooting a ray through another piece. This interaction path is also the foundation for Chaos.

### 8. Preserve a clean future boundary for Chaos

Do not implement Chaos in this release. Do not scatter `if (chaos)` branches yet. Add only the configuration mode discriminator needed to recognize unsupported modes safely. State authority rejects match start unless `GameplayMode == TurnBased`; add an automated test for unknown and reserved values.

When Chaos begins, extract:

- turn validation from `ChessNetworkGameState.RPC_RequestMove`;
- turn completion from `ChessGameController.CompleteTurn`;
- win evaluation from `EvaluateGameState`; and
- per-piece timing/weight from interaction code.

At implementation time, mark the speed-first branches with:

```csharp
// gstack-shortcut(dec-a2ddb89a): 7/10, upgrade when Chaos starts or variant branches affect 3+ workflows.
```

## Failure and Edge Cases

- A guest joining before configuration replication completes sees `Loading match settings…`; Ready stays disabled.
- Ready carries the accepted revision; stale or delayed requests are rejected.
- A disconnected or replaced seat clears only its pre-match accepted revision. During Playing, reconnect uses persistent MatchPhase and the existing reconnect window instead of Ready state.
- A host leaving during Configuring closes the room for the guest. A host leaving during Playing uses the existing authority handoff and reconnect rules.
- Unsupported `SchemaVersion` rejects match start with an explicit build-mismatch message.
- Any `GameplayMode` other than `TurnBased` rejects match start with an explicit unsupported-mode message.
- Chess960 uses a validated index in `0..959`. Rematch generates a guaranteed-different index once after both players accept; repeated button presses cannot reroll it.
- Standard games ignore the round position index and preserve current placement/castling behavior exactly.
- Podiums created by an earlier room cannot remain visible in a ground-level room.
- MatchPhase progresses Configuring → Playing → Ended and never moves backward during reconnect.

Rematch is the one intentional lifecycle loop. When both votes arrive while Ended, state authority performs one transaction: increment `RoundSequence`; select a guaranteed-different `RoundChess960Index` when applicable; reset board, Three-check counters, clocks, outcome, and rematch flags; write one complete sequence-tagged authoritative snapshot; then change `MatchPhase` from Ended to Playing. Clients must never observe Playing with the previous round's snapshot, and authority rejects move requests carrying an older sequence.
- Both Quest and Editor clients must use a matching build because Fusion's networked layout changes.

## Test Plan

### Edit-mode rules tests

- Generate every one of the 960 legal Chess960 positions exactly once from the supported index mapping.
- Assert opposite-color bishops, king between rooks, mirrored Black placement, and stable generation.
- Cover every Chess960 castling shape, including king-only, rook-only, and transposition cases.
- Reject castling when the king path or rook path is obstructed, a required final square is illegally occupied, the king is in check, or a king transit/destination square is attacked.
- Verify atomic castling requests initiated by king movement and stationary-king rook movement.
- Verify the third legal check wins, double check counts once, illegal moves do not count, and checkmate still wins.
- Verify check counters participate in repetition identity and third-check outcome wins the display-precedence tie with checkmate.
- Verify Standard reset and castling remain byte-for-byte equivalent to current behavior.

### Network tests

- Host configuration replicates to the guest.
- Guest cannot modify configuration.
- Match cannot start until the guest accepts the exact replicated revision.
- A stale Ready request cannot start a match.
- Initial start publishes one complete board snapshot before exposing Playing; clients cannot observe Playing with an empty or previous board.
- Delayed move requests and snapshots from an older `RoundSequence` cannot affect the current round.
- Creator departure during Configuring closes the pre-match room; departure during Playing follows reconnect/authority handoff.
- Initial Chess960 board is identical on Quest and Editor.
- Rematch produces a guaranteed-different `0..959` position and an identical new board on both clients.
- Reserved or unknown GameplayMode values cannot start a match.
- Authority handoff preserves configuration and counters.

### Headset tests

- Every control is comfortably targetable by controller ray at the current 2.1 m panel distance.
- No page requires scrolling.
- Create/Wait remains one panel with room code and summary.
- Guest can understand the match before pressing Ready.
- Podium & Overview off produces ground-level play and no Overview button.
- From ground level, perimeter teleport and direct grab can reach all 32 starting pieces.
- Overview remains an independent local toggle when enabled.

## Success Criteria

- The host can configure and create all four turn-based combinations.
- The guest sees the same settings and cannot start on a stale configuration revision.
- Both devices always show the same Chess960 position.
- Chess960 castling passes automated edge-case tests.
- Three-check counters and outcomes replicate correctly.
- Rematch creates a fresh Chess960 position while preserving other settings.
- Existing Standard multiplayer, reconnect, clocks, avatars, result screen, and room-code flow still work.
- The configuration fits the existing VR panel with no second popup or webpage-style UI.
